# Как писать тесты для задач

Тесты запускаются в браузере внутри Web Worker. Проверка идёт на 144 задачах NeetCode 150 (кроме 6 встроенных и 3 пилотных: `is-palindrome`, `reverse-a-linked-list`, `lru-cache`, их уже сделали).

Образец — `tests/groups/g0-pilot.js` и `tests/refs/g0-pilot.js`. Прочитай их первыми.

## Файлы, которые ты создаёшь (ровно два, больше ничего не трогай)

1. `tests/groups/<группа>.js` — код для браузера. Оберни всё в `(function () { ... })();`, потому что все группы склеиваются в одну область видимости. Внутри присваивай `NC_TESTS['slug'] = { ... }`.
2. `tests/refs/<группа>.js` — только для Node: `module.exports = { 'slug': { ref: '<исходник верного решения>', wrong: '<исходник заведомо неверного решения>' } }`.

Проверка: `node scripts/verify-tests.js <группа>` (имя файла без `.js`). Она должна закончиться без `FAIL`. Не запускай `embed-tests.js` и `build.js`, не меняй `src/`.

## Поля задачи

```js
NC_TESTS['slug'] = {
  fn: 'isPalindrome',              // имя функции (или класса), которую пишет ученик
  starter: 'function isPalindrome(s) {\n  // твой код\n}\n',   // заготовка для редактора
  cmp: 'exact',                    // как сравнивать ответ
  wrap: 'function __t(arr) { ... }', // необязательно
  tests: function () { return [ { args: [...], expected: ... }, ... ]; }
};
```

### tests()
Возвращает массив `{ args, expected, label? }`.
- Тесты **без** `label` — «примеры», их гоняет кнопка «Запустить». Нужно 3–6 штук: первыми идут примеры из условия (текст условия и примеры лежат в `src/app.html`, блок `<script id="stmts">`, объект `NC_STMTS[slug] = [условие, примеры, ограничения]`), затем крайние случаи.
- Тесты **с** `label` — большие, их гоняет только «Отправить». Нужно 1–3 штуки там, где ограничения делают медленное решение невозможным (метка вида `'большой тест: 100 000 чисел'`). Эталон на всех тестах вместе должен работать быстрее 1 секунды в Node. Весь набор в браузере ограничен 5 секундами.
- `args` и `expected` только JSON-совместимые (без undefined, NaN, Infinity, функций; пустое значение это `null`). `args` — массив позиционных аргументов.
- Генерация тестов должна быть быстрой (меньше 300 мс).
- Ожидаемые ответы считай независимо от эталона: вручную, по построению или простым перебором прямо в файле тестов. Не вызывай эталонное решение из тестов.

Доступны помощники: `range(n, f)`, `lcg(seed)`, `shuffled(arr, seed)` (детерминированные), объект `CMP`.

### cmp
Строка из `CMP` (`'exact'`, `'sortedNums'`, `'setOfArrays'` — внешний порядок не важен, `'setOfSets'` — не важен и порядок внутри вложенных массивов, `'float'` — допуск 1e-5) или функция `function (result, args, expected) { return true|false; }`. Если у задачи несколько верных ответов (любой порядок, любая из нескольких подстрок и т. п.), пиши свою функцию-валидатор, которая проверяет ответ по условию.

### wrap
Строка с исходником функции `__t`. Она выполняется в одной области с кодом ученика и может вызывать его функцию или класс по имени. Тест вызывает `__t(...args)`, а не `fn`. Нужна, когда вход или выход не JSON (списки, деревья, графы, классы) или когда решение меняет вход на месте (тогда `__t` вызывает функцию ученика и возвращает изменённую структуру).
Доступно `__H`: `ListNode`, `TreeNode`, `arrToList(arr, pos)` (pos ≥ 0 замыкает хвост в цикл), `listToArr(head)`, `arrToTree(levelOrderArr)`, `treeToArr(root)` (формат как на LeetCode, `null` для пустых мест), `runDesign(Cls, ops, args)` для дизайн-задач (`ops[0]` имя класса, `args[0]` аргументы конструктора; для void-методов результат `null`). Другие вспомогательные функции (граф, список с random и т. п.) определи прямо внутри строки `wrap`.
Если задача из двух функций (например, encode и decode), поставь `fn` на первую, а в `wrap` сделай `__t` с проверкой «туда и обратно».

### starter
Сигнатура в стиле LeetCode на JavaScript, camelCase, с телом `// твой код`. Для списков и деревьев добавь сверху комментарий с определением `ListNode` или `TreeNode`. Для классов дай каркас класса с методами. Имена параметров должны совпадать с условием.

## refs
- `ref` — верное решение, оптимальное по сложности. Он ссылается на те же имена, что и starter. `ListNode` и `TreeNode` доступны, если ученик их не объявил.
- `wrong` — правдоподобное неверное решение (ошибка на единицу, забытый крайний случай, лишь часть условия). Оно обязано проваливать минимум один тест. Для задач, где важна скорость, лучше, чтобы наивный перебор не укладывался в большие тесты.

## Требования к качеству
- Тесты обязаны соответствовать тексту условия из `NC_STMTS` и ограничениям в нём. Если в условии нашлась неточность или двусмысленность, не правь `src/app.html`, а напиши об этом в отчёте.
- Хорошо покрой крайние случаи: пустой вход, один элемент, повторы, отрицательные числа, границы ограничений.
- Не делай тесты, которые зависят от версии браузера или времени.
